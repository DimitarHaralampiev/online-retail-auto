# Repository Guidelines

## Project Overview

`online-retail-auto` is a bilingual (Bulgarian/English) online shop for car accessories and parts in Bulgaria with its own warehouse. Stack: Next.js 16 App Router, React 19, TypeScript (strict), PostgreSQL 17 (`pg`), Zod validation, Stripe (test mode) and Nodemailer. Optional integrations: OpenAI (invoice reading and business insights; paid usage, server-only keys) and the Speedy courier API. The storefront catalog is served through a `CatalogRepository` backed by demo data (`src/lib/catalog-demo-data.ts`); the PostgreSQL adapter is tracked in epic #12. The roadmap lives in GitHub epics #11–#17.

The `.agents/`, `.aws/`, `.codex/` and `.idea/` directories are local environment configuration; do not treat them as application modules or commit their contents.

## Project Structure

- `src/app/` — App Router pages (including `catalog`, `cart`, `checkout`, `account`, `orders`, `garage`, `favorites`, `for-you`, `promotions`, `inventory-demo`, `admin/*`) and route handlers under `src/app/api/`.
- `src/components/` — React components; client components carry `"use client"`.
- `src/lib/` — domain logic, data access and validation (catalog, pricing, inventory, checkout, orders, accounts, invoices, delivery). Unit tests sit next to the code as `*.test.ts`.
- Catalog access: server code calls `catalog()` from `src/lib/catalog-server.ts` (a `CatalogRepository`); client components use `useCatalog()` from `src/components/catalog-provider.tsx`. Never import `catalog-demo-data` outside the static adapter wiring, tests and scripts (ESLint enforces this). See `docs/architecture/`.
- `src/lib/i18n/` — locale handling and English translations (`en.json`); Bulgarian is the source language: write UI strings in Bulgarian and add the English entry to `en.json`, keyed by the whitespace-normalised Bulgarian text.
- `db/` — numbered SQL migrations (`NNN-name.sql`). `scripts/migrate.mjs` has no tracking table and re-applies every file in order, each in its own transaction, on every run, so each migration must be idempotent (`IF NOT EXISTS`, `ON CONFLICT`, guarded `ALTER`s) and must stay safe to re-run. Schema reference: `docs/database-schema.md`.
- `scripts/` — operational scripts (migrations, admin grant, workers, DB-backed flow tests).
- Vehicle fitment: `src/lib/vehicles.ts` over `vehicle_makes`/`vehicle_models`/`vehicle_generations`/`vehicle_engines` and `product_vehicle_fitments` (ADR `docs/architecture/0002-vehicle-fitment.md`). Reference and fitment data come only from a verified source, never from migrations, seeds or guesses; tests use fictional fixtures. Admins maintain the reference at `/admin/vehicles` (CSV import with dry run in `src/lib/vehicle-import.ts`: one row per engine of a generation, each row the full record; makes and models are hidden, never deleted). Product fitments are edited on the product page (`/admin/products/edit`) or imported at `/admin/vehicles` (`src/lib/fitment-import.ts`, `src/lib/admin-fitments.ts`); each names its verification source and appears in the product's audit history. `GET /api/vehicles?level=makes|models|generations|engines&parent=<id>` serves the public, cacheable lookups for selectors. Shoppers pick their car in the catalog selector (`src/components/vehicle-selector.tsx`, shown only with `CATALOG_SOURCE=postgres`); `/api/vehicle-selection` keeps it in the `auto_vehicle` cookie (ids only, re-resolved on every read) and can save it to the signed-in customer's garage (`garage_vehicles.generation_id`/`engine_id`, migration 015). With a car selected, the catalog's "only my car" filter runs in the browse SQL (`BrowseQuery.vehicle`, PostgreSQL adapter only) and product cards get fit badges from `fitStatuses` (fits / universal / check; no badge without verified data); product pages list verified fitment. The old free-text `product_fitments` table is gone (migration 016). Landing pages `/cars`, `/cars/[make]` and `/cars/[make]/[model]` (`src/lib/car-pages.ts`) list active makes and models and the published products with verified fitment; they return 404 without `CATALOG_SOURCE=postgres`.
- `docs/` — integration notes, reference reviews and screenshots. `public/images/` — product and design images.

## Toolchain and Commands

Node.js 22 LTS (`.nvmrc`; minimum 20.18.1 per `engines`) and npm. Install with `npm ci`.

- `npm run dev` — development server on http://localhost:3000.
- `npm run format:check` / `npm run format` — Prettier.
- `npm run lint` — ESLint (Next.js core-web-vitals + TypeScript rules, `eslint.config.mjs`). Errors and warnings both fail (`--max-warnings 0`); the React Compiler rules (`react-hooks/set-state-in-effect`, `react-hooks/refs`) apply everywhere — derive state, key a component to reset it, or use `useSyncExternalStore` for browser storage instead of setting state in effects.
- `npm run typecheck` — TypeScript without emit.
- `npm test` — unit tests with the Node.js test runner via `tsx`. The glob is not recursive: only top-level `src/lib/*.test.ts` files run.
- `npm run test:integration` — PostgreSQL integration tests in `tests/integration/`. Each test file gets its own freshly migrated database (migrations applied twice to prove idempotency) that is dropped afterwards. Uses `TEST_DATABASE_URL`, or locally the server from `DATABASE_URL` in `.env.local`; non-local hosts and `host`/`hostaddr` query overrides are refused; databases left by killed runs are swept automatically. Use `setupTestDatabase()` from `tests/integration/database.ts` for new database tests.
- `npm run test:e2e` — Playwright browser tests in `e2e/` (desktop and mobile Chromium): shopping journeys up to the checkout preview plus an axe WCAG 2.1 AA scan that fails on serious or critical violations. It builds and starts the app on port 3100 with offline demo courier data and no database (set `E2E_BASE_URL` to test a running app). `npm run test:e2e:docker` runs the same suite in the official Playwright image when the host lacks browser libraries (e.g. WSL); it reuses the host `node_modules` (Linux x64 only) and the shared `.next`, so stop other builds first. Locally a server already on port 3100 is reused. Prefer role and label locators.
- `npm run build` / `npm start` — production build and server.
- Local services: copy `.env.example` to `.env.local`, then run `LOCAL_DB_PASSWORD=<password> docker compose up -d` (Postgres on 127.0.0.1:5433, Mailpit SMTP 1025 and UI http://localhost:8025). The password must match the one in `DATABASE_URL`; compose does not read `.env.local`.
- `npm run db:migrate` — apply all migrations using `.env.local`.
- Catalog source: `CATALOG_SOURCE=postgres` serves the catalog from PostgreSQL (seed it first); unset or `static` uses the built-in demo data, as builds and browser tests do.
- `npm run db:seed:demo` — load the demo catalog (categories, translations, published products, stock, demo promotion) into the database. Idempotent; never resets stock or touches non-demo products; refuses a non-local `APP_URL` unless `ALLOW_DEMO_SEED=1`. Migrations never contain catalog data.
- Legal pages: `/legal/terms|privacy|delivery|returns|cookies` show business-supplied texts edited at `/admin/legal` (`legal_pages`, migration 021; `src/lib/legal.ts`), rendered from a safe Markdown subset (`src/lib/legal-markdown.ts`, never raw HTML). Empty text shows a not-yet-published notice and is noindex. Trader details come from `COMPANY_*` settings. Never write legal text in code.
- Cookie consent (`src/lib/consent.ts`, `src/components/consent-provider.tsx`): necessary cookies (session, language, chosen car, cart) need no consent. Any analytics or marketing code must render inside `<ConsentGate category="analytics|marketing">` and its service be declared with `ANALYTICS_PROVIDER`/`MARKETING_PROVIDER`; that turns on the banner (accept and refuse equally easy, choice in `auto_consent`, versioned). With none configured there is no banner.
- Returns (`src/lib/returns.ts`, migration 022): admins mark handed-over orders `delivered` (until courier tracking, #55), which starts the 14-day withdrawal period. Signed-in customers request returns of their own delivered order lines on the order page (`/api/orders/[id]/returns`); admins approve, reject and receive them at `/admin/returns`. Receiving puts stock back (`stock_movements` 'return', PostgreSQL catalog) and records the goods value to refund (`refund_cents`), which joins the refund queue.
- Payments and refunds (`src/lib/refunds.ts`, migration 026): paid card payments (Stripe webhook, simulator) are recorded once in `payments`. Money owed back is a `refunds` row (`requested` → `succeeded`): a payment that arrives for an already cancelled order, or a received return. `/admin/orders` lists open refunds; an admin pays out in Stripe or by bank transfer and marks it done (audited). `checkoutPayment` stores a Stripe session and extends the reservation only under the order lock while the order is still payable.
- Reviews (`src/lib/reviews.ts`, migration 023): only signed-in customers with a delivered order containing the product may review it, once; reviews appear after an admin publishes them at `/admin/reviews`. Ratings shown on product pages and in JSON-LD `aggregateRating` come only from published reviews (never seed or invent reviews). Authors are shown as first name and last initial.
- Newsletter (`src/lib/newsletter.ts`, migration 024): footer sign-up with an explicit consent checkbox (wording in `src/lib/newsletter-text.ts`, stored with the subscription); double opt-in via `/newsletter/confirm` (7-day link), `/newsletter/unsubscribe` from every email; links carry fragment tokens and act only on click; the same answer whether or not an address is known. Only `confirmed` addresses may receive newsletters.
- Security headers (#51): `src/proxy.ts` sets a per-request nonce CSP (`src/lib/security-headers.ts`; scripts need the nonce, no `unsafe-inline` scripts, no `eval` in production); `next.config.ts` adds nosniff, frame denial, referrer and permissions policies and HSTS in production. Never add inline `<script>` code without the nonce (data blocks like JSON-LD are fine). Per-client limits (`src/lib/request-limits.ts`, in memory): sign-in/registration 20/15 min, orders 10/10 min, AI calls 30/hour per admin — running `test:orders` and `test:features` repeatedly within 10 minutes can hit the order limit (restart the dev server to reset).
- Observability (#52, ADR `docs/architecture/0005-observability.md`): log with `log()`/`logError()` from `src/lib/log.ts` (JSON lines, secrets redacted, emails and phone-like numbers scrubbed), never bare `console.error` in `src/` (the CLI workers in `scripts/` still print plainly until #53); every handled server failure goes through `logError(message, error)`, which also reports it. `src/proxy.ts` gives each page and API request an `x-request-id` (returned in the response). `src/instrumentation.ts` captures unhandled errors. With `SENTRY_DSN` errors go to Sentry via its envelope API (no SDK, no request data). Probes: `GET /api/health` (readiness, database, 503 on failure) and `GET /api/health?probe=live`.
- Password recovery (`src/lib/password-reset.ts`, migration 020): `forgot`/`reset` actions on `/api/account`, page `/account/reset`. Single-use 30-minute tokens (hash stored, link token in the URL fragment), per-account and per-client limits, the same answer whether or not the account exists (work runs after the response), and a reset signs the account out everywhere.
- `npm run admin:grant -- <email>` — grant the admin role to an existing account with a verified email.
- Admin product management lives at `/admin/products` (list, create/edit at `/admin/products/edit`, media at `/admin/products/media`, categories at `/admin/categories`) on the `/api/admin/catalog/products` and `/api/admin/catalog/categories` routes. Category slugs are storefront URL ids and fixed at creation; categories are deactivated, never deleted, and stay at most two levels deep. Re-running the demo seed resets demo categories' parent, order and names (not their active flag) and does not check the two-level rule, so on demo data avoid nesting real categories under demo ones. Moving a category changes its storefront URL; old links are not redirected. New products start as drafts without stock; publishing requires a price and an active category. It needs `CATALOG_SOURCE=postgres` for changes to reach the storefront. Invoice receipts match an existing SKU by brand, manufacturer code and EAN (case-insensitive): empty fields count as unknown and are filled from the invoice, but a product with any known field needs at least one match.
- Catalog search: the search box (`q`) becomes `BrowseQuery.search`. With PostgreSQL it ranks by relevance over `product_search` (migration 017: full text, `pg_trgm` typo tolerance, Bulgarian Cyrillic↔Latin via `search_latin`, both languages); an exact SKU, manufacturer code or EAN shows only that product. The static demo matches it literally like `text`. `text` stays the literal substring filter. Autocomplete goes through `searchProvider(locale)` (`src/lib/search.ts`, ADR `docs/architecture/0003-search-provider.md`, which also records when to adopt a search engine); `latinize()` in `src/lib/search-text.ts` mirrors `search_latin`. The header search is an ARIA combobox (`src/components/search-autocomplete.tsx`) fed by `GET /api/search/suggest?q=&locale=` (no-store, rate limited per client with `src/lib/rate-limit.ts`; in-memory per instance, shared limits are #51).
- Facets: `CatalogRepository.facets(query)` returns counts under every other active filter (disjunctive). The brand facet groups `warehouse_products.brand` by `brand_key()` (migration 018; `brandKey()` in `src/lib/search-text.ts` mirrors it); the URL carries repeatable `brand=` keys. The static demo has no brands, so its facets are empty.
- SEO metadata: public pages build theirs with `pageMetadata()` (`src/lib/seo.ts`): canonical and hreflang alternates (Bulgarian at the plain URL and `x-default`, English at `?lang=en`, which `src/proxy.ts` turns into the request language and the locale cookie), Open Graph and robots. Everything is `noindex` unless `SITE_INDEXABLE=1`; the root layout keeps private pages noindex. Filtered or searched catalog URLs are noindex with the category as canonical. `/robots.txt` (`src/app/robots.ts`) disallows everything until then, otherwise lists the sitemaps: `/sitemap.xml` (pages, categories, car pages) and `/sitemaps/products/N` (10,000 visible products each, both languages with alternates, `CatalogRepository.listProductSkus`). Structured data (`src/lib/structured-data.ts`, rendered by `src/components/json-ld.tsx`): Product/Offer and BreadcrumbList on product pages, BreadcrumbList on category pages, WebSite with SearchAction on the home page; only catalog facts (no ratings, reviews, condition or brand claims).
- Caching and performance (ADR `docs/architecture/0004-caching-and-performance.md`): only the taxonomy is cached across requests (`src/lib/catalog-cache.ts`, tag `catalog`, 5 min), expired by `refreshStorefront()` on every admin change; prices, stock and products stay per request. `e2e/performance.spec.ts` enforces LCP/CLS/interaction/JavaScript budgets in CI.
- Product media: uploads go through `src/lib/media-storage.ts` — bytes in `product_media.content` (`MEDIA_STORAGE=database`, default) or an S3-compatible bucket (`MEDIA_STORAGE=s3` with `S3_*`, signed by `src/lib/s3-storage.ts`; `storage_key`, migration 019). Shoppers get images of published products at `/media/<id>` (immutable caching; videos and drafts stay admin-only), and the primary image is the storefront product image (`next/image` optimises it).
- Bulk product import: `/admin/products/import` (API `/api/admin/catalog/imports`, logic in `src/lib/product-import.ts`). Upload a UTF-8 CSV (`;` or `,`, up to 2 MB and 2000 rows; split larger catalogs) with the columns listed on the page; a check (dry run) reports every row, and apply commits only when no row has an error. Empty cells keep existing values; `stock` books opening stock for new products only.
- `npm run worker` — the background worker (#53, `scripts/worker.ts`, `src/lib/worker.ts`, ADR `docs/architecture/0006-background-jobs.md`); production must run it continuously (`-- --once` runs every job once). It delivers order emails (every 15 s) and customer emails (every minute), scans customer notifications (every 5 min) and releases stock held by unpaid card orders whose payment window passed (every minute; cancels them and emails the customer — without the worker unpaid card orders hold stock indefinitely). Each job holds a PostgreSQL advisory lock, so extra instances never run one job twice at once; SIGTERM finishes the running job. Email delivery (`src/lib/email-outbox.ts`, migration 025): emails are queued in the transaction of the change they report and delivered at least once — leased rows (SKIP LOCKED, 5-minute lease), SMTP outside transactions, exponential backoff from 1 minute to 6 hours, failed (dead letter) after 10 attempts or at once for a rejected recipient; `/admin/orders` shows failed emails and "send again" requeues them. The older `npm run orders:release-expired`, `orders:send-emails` and `customers:worker` run single jobs and remain for manual use. With `CATALOG_SOURCE=postgres`, orders reserve stock in the order transaction (`src/lib/stock-reservations.ts`); handover consumes and cancellation releases it.
- `npm run mail:check` — verify SMTP settings.
- `npm run test:orders`, `npm run test:features` — end-to-end smoke flows. They need a running local app (`npm run dev`, or set `TEST_APP_URL`), a migrated local database, and Mailpit (`test:orders` also needs `PAYMENT_PROVIDER=simulator`), and refuse non-local targets.

Run format check, lint, typecheck, unit tests and build before opening a pull request. GitHub Actions (`.github/workflows/ci.yml`) runs the production dependency audit and these checks on every pull request and on `main`; Dependabot proposes weekly grouped dependency updates.

## Coding Style & Naming Conventions

Follow the existing patterns: TypeScript everywhere, Zod schemas for external input in new code, money as integer cents (`*_cents`) and rates as basis points (`*_bps`). Keep server-only secrets out of client components and never prefix them with `NEXT_PUBLIC_`. Use descriptive names and small modules; avoid unrelated formatting changes.

## Testing Guidelines

Add tests alongside new behavior in `src/lib/*.test.ts` using `node:test` and `node:assert`. Cover normal behavior, edge cases and failure paths; add a regression test for bug fixes. Do not claim checks passed without running them, and state explicitly in PRs when a check could not run.

## Commit & Pull Request Guidelines

Do not commit directly to `main`; merge through pull requests. Work on one branch per issue — `feature/<issue>-<slug>`, `fix/<issue>-<slug>` or `chore/<issue>-<slug>`. Use concise, imperative commit messages, for example `Add inventory import workflow`. Pull requests link their issue (`Closes #N`), describe the problem, resulting behavior and validation, and include screenshots for visible UI changes.

## Security & Configuration

Never commit credentials, tokens, customer data or local environment files (`.env*` except `.env.example`). Add placeholder values to `.env.example` and document required settings. Every API route authorizes on the server: customer and order data are scoped to the session's customer, never to a client-supplied ID; admin routes check the admin role with `currentCustomer(request)`/`currentAdmin(request)` (the session comes from the request's Cookie header); keep the origin check on state-changing routes (`requestJson`, or `requireSameOrigin` for uploads — never a hand-rolled copy). `tests/integration/admin-routes.test.ts` discovers every route under `src/app/api/admin` and checks 403 for anonymous and non-admin callers, 400 for a foreign, `null` or missing Origin, 400/404 for invalid input and 503 without details for database errors, so new admin routes are covered automatically; verify Stripe webhooks with `constructEvent`. Keep `ORDER_TRACKING_SECRET` and API keys server-only. Do not invent legal text, ratings, vehicle fitment or commercial claims.
